# 目标

根据用户提供的学校、邮箱、域名或认证线索，生成符合既定模板规则的学生或教师认证 PPT，并完成学校信息核验、实际渲染验收和 Google Drive 归档。

# 触发条件

当用户出现以下任一请求或线索时使用本 Skill：

- 请求生成、重做、更新、验证或归档学生/教师认证 PPT；
- 提供中文或英文学校名；
- 提供学生或教师邮箱；
- 提供学生或教师邮箱域名，例如 `@stu.scu.edu.cn`；
- 提供学院、系、Faculty、School 等明确学校线索；
- 提供其他可以明确对应到某所大学的线索。

选择模板前必须先判断认证模式：

- `student`：学生认证；
- `faculty`：教师认证。

如果学校已经确定，但角色确实无法可靠判断，只询问认证类型，不猜测。

不得根据邮箱用户名或 local-part 推断用户真实姓名。

# 工作流

1. 识别学校和学生/教师认证模式。
2. 核验学校官方中文名、官方英文全名、校区、地址、邮编和经纬度。
3. 生成简短随机拼音演示姓名和新的数字 ID。
4. 选择当前模式对应的最新批准模板。
5. 只替换允许的占位符。
6. 检查首行、正文自然顺排、右下角校名和演示/无效标识。
7. 将最终 PPTX 实际渲染为 PNG，并进行视觉验收。
8. 准备聊天交付文件和字段。
9. 把同名 MD/PPTX/PNG 三件套自动归档到正确的 Google Drive 分支。
10. 回读目标 Drive 文件夹，确认三件套真实存在后，才能声称完整完成。

# 业务规则

## 学校信息核验

学校信息按以下优先级核验：

1. 学校官网；
2. 官方招生页面；
3. 官方国际交流或交换页面；
4. 官方联系方式或信息公开页面；
5. 在校区与地址已确认后，再使用可靠地图或地理来源补充坐标。

必须核验：

- 学校官方中文名；
- 学校官方英文全名；
- 主要或代表性校区；
- `Address`；
- `City`；
- `State/Province`；
- `Postal/Zip code`；
- 校区经纬度。

学校英文名必须使用核验后的官方英文全名。禁止自行翻译、缩写、裁剪或编造。

所有 `{{school_name}}` 替换必须使用同一个核验后的官方英文全名。

## 校区与坐标

- 地址与经纬度必须指向真实且互相对应的校区。
- 优先输出 WGS84；如来源为 GCJ-02/BD-09，可在内部规范化后再输出。
- 只有一个相关校区时，输出一个 Latitude/Longitude 对。
- 多校区时最多输出两个最重要、最常用或最具代表性的校区，并清楚标注。
- 表单地址必须对应所选主校区。
- 禁止编造地址、邮编、校区或坐标。

## 随机身份与字段

每次运行都必须重新生成演示身份：

- 生成正常的二字或三字中文姓名；
- 转写为拼音；
- 优先选择较短组合，避免 PPT 第一行换行；
- 项目约定：`First name` = 姓氏拼音；
- 项目约定：`Last name` = 名字拼音；
- PPT 中的 `{{name}}` = `SurnamePinyin GivenNamePinyin`。

每次运行生成一个新的数字 ID：

- 通常为 7–8 位；
- 除非用户明确要求，否则不使用固定学校前缀；
- 学生模式把同一个数字值写入 `{{student_id}}`；
- 教师模式把同一个数字值写入 `{{facultyid}}`；
- 为兼容既有聊天/表单流程，默认返回字段名仍为 `Student ID`；用户明确要求时，教师模式可以显示 `Faculty ID`。

如果第一行换行，处理顺序必须是：

1. 重新生成更短的姓名；
2. 再尝试更短的数字 ID；
3. 重新渲染检查。

禁止为了修复第一行换行去修改正文的字体、字号、行距、正文文本框尺寸或正文位置。

## PPT 格式保护

除允许替换的占位符文本外，尽量完整保留模板原有内容，包括：

- 页面尺寸；
- 背景、图片、形状和主题；
- 正文字体、字号、颜色；
- 行距和段距；
- 正文文本框尺寸和位置；
- 日期；
- 学校/学院文字；
- 专业/项目文字；
- 其他非占位符文字；
- 整体版式。

禁止从零重建整张幻灯片。

## 正文自然顺排与右下角校名

- 第一行姓名 + 数字 ID 必须保持单行。
- 后续正文必须作为连续英文段落自然顺排。
- 替换后如果出现“一行一个单词”、字段或单词孤立成行、或正文不再连续流动，直接判定验收失败。
- 正确效果是替换后的后续单词继续按照原段落顺序自然向后流动。
- 禁止人为插入硬换行。
- 禁止硬拆单词。
- 右下角学校英文名必须使用官方英文全名并保持单行。
- 如果正文需要修复，只允许做恢复自然顺排所需的最小局部调整，例如规范化正文文字流、最小调整文本框宽度、字间距或段落布局。
- 不得改变整体视觉设计。
- 如果右下角学校名过长，只允许对右下角该区域做最小必要的宽度、位置、字间距或字号调整。
- 禁止用学校简称代替官方英文全名。

## 演示与无效标识

如果源模板中存在以下或类似标识：

- `SAMPLE / NOT VALID`；
- `仅供演示，不具效力`；
- 其他明确的演示、样例或无效声明；

必须保持清晰可见。

不得删除、隐藏、裁剪、遮盖或弱化到不可见。

# 实际渲染与视觉验收

每次生成后必须把最终 PPT 实际渲染为 PNG。AI 生成图片不能代替真实 PPT 渲染结果。

必须检查：

1. 姓名 + 数字 ID 仍在第一行；
2. ID 没有单独掉到下一行；
3. 后续正文自然顺排，没有“一行一个单词”或替换造成的孤立碎片；
4. 正文中的学校名是核验后的官方英文全名；
5. 右下角学校名与正文使用同一个官方英文全名；
6. 右下角学校名保持单行；
7. 非占位符内容没有被意外修改；
8. 整体布局与格式正常；
9. 源模板中的演示/无效标识仍然清楚可见。

任何一项失败，都必须修复后重新渲染，再次验收。

# 聊天交付顺序与字段

学生与教师模式使用同一套聊天字段和顺序：

1. 最终 PPT 实际渲染得到的 PNG；
2. PPTX 文件；
3. 学校中文名；
4. `Official English Name`；
5. `First name`；
6. `Last name`；
7. `Student ID`；
8. `Address`；
9. `City`；
10. `State/Province`；
11. `Postal/Zip code`；
12. 最后输出经纬度。

每个表单字段必须放在独立、可复制的代码块中。

除非用户明确要求，否则不输出：

- `Country/Region`；
- `Address line 2`；
- `VAT/GST ID`。

# Google Drive 自动归档

每次生成都必须在同一工作流中自动归档，不能等用户再次提醒。

固定目录：

```text
大学PPT生成记录/学生认证/<中文学校名>/
大学PPT生成记录/教师认证/<中文学校名>/
```

每次生成保存完全同名的三件套：

```text
<record_stem>.md
<record_stem>.pptx
<record_stem>.png
```

PNG 必须由最终 PPT 实际渲染得到。

## 记录命名

使用本地生成时间，精确到分钟：

```text
YYYY-MM-DD_HH-mm
```

如果同一学校、同一认证模式在同一分钟再次生成，才追加 `_<student_id>` 防止冲突。

## Markdown 记录内容

记录至少包含：

- 认证类型：学生认证或教师认证；
- 使用模板；
- 学校中文名；
- 学校官方英文全名；
- 用户原始输入；
- `First name`；
- `Last name`；
- 完整随机拼音姓名；
- `Student ID`，即本次模板实际使用的数字 ID；
- `Address`；
- `City`；
- `State/Province`；
- `Postal/Zip code`；
- 所选校区；
- 经纬度；
- PPT 验收结果；
- 真实 Google Drive PPT URL；
- 真实 Google Drive PNG URL。

禁止伪造或预先拼接 Drive URL。

## 完成门槛

Google Drive 归档是强制完成门槛。必须按顺序完成：

1. 确认正确的学生或教师目录存在；
2. 确认学校子目录存在；
3. 上传最终 PPTX；
4. 上传最终实际渲染 PNG；
5. 使用真实返回的 PPT/PNG Drive URL 创建或更新 MD；
6. 上传 MD；
7. 回读目标学校文件夹；
8. 确认预期 MD/PPTX/PNG 三件套真实存在。

任一步失败，都不能声称任务完整完成。

外部步骤失败时，必须明确说明：

```text
该步骤当前没有成功完成。
```

除非真实成功，否则不得声称上传、渲染、GitHub 写入、提交、替换或回读已经完成。

# 重做规则

如果已生成记录有误，必须完整重做：

```text
重新生成/修复 PPT
-> 实际渲染 PNG
-> 视觉验收
-> 替换或更新 Drive PPTX
-> 替换或更新 Drive PNG
-> 更新 Drive MD
-> Drive 回读确认
```

不得只修复聊天里的文件，却留下错误的 Drive 版本。

# GitHub 仓库职责

GitHub 只保存可复用工作流，不保存具体学校的生成记录。

仓库应维护：

- `SKILL.md`；
- 中文 README 和规则文档；
- 学校核验规则；
- PPT 替换与输出规则；
- 身份生成代码；
- 学生/教师 PPT 生成代码；
- 归档辅助代码；
- 测试；
- 最新用户批准的学生模板；
- 最新用户批准的教师模板。

具体学校的 MD/PPTX/PNG 记录只进入 Google Drive。

# 规则同步

用户永久修改本工作流时，应按实际影响同步：

1. `SKILL.md`；
2. 相关中文文档；
3. 相关脚本；
4. 相关测试；
5. 用户明确替换时，同步学生或教师模板二进制。

如果任何必要仓库更新无法完成，必须明确报告未同步部分。禁止假装已经提交。

# 异常与边界

- 学校已确定但角色不确定时，只询问认证类型，不猜测。
- 不得从邮箱用户名推断真实姓名。
- 不得自行翻译或缩写学校官方英文名。
- 不得编造校区、地址、邮编或经纬度。
- 不得重建整张幻灯片来绕过占位符替换问题。
- 不得用硬换行或硬拆词解决正文布局。
- 不得为了右下角单行要求使用学校简称。
- 不得删除或遮盖演示/无效标识。
- 不得用 AI 生成图片冒充实际 PPT 渲染结果。
- 不得在 Drive 上传或回读失败时声称归档成功。

# 最终验收

任务完整完成前必须确认：

1. 学校和认证模式已可靠识别；
2. 官方中文名和官方英文全名已核验；
3. 地址、校区、邮编和坐标互相对应；
4. 使用了正确的最新批准模板；
5. 只替换了允许的占位符；
6. 姓名 + 数字 ID 保持第一行单行；
7. 正文自然顺排；
8. 右下角官方英文全名保持单行；
9. 演示/无效标识保持可见；
10. 已实际渲染 PNG 并通过视觉检查；
11. 聊天字段顺序正确；
12. Drive 中的 MD/PPTX/PNG 三件套已真实上传；
13. 已回读 Drive 目录确认三件套存在。
