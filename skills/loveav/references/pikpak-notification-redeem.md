# PikPak 通知关键词批量兑换

这是 LoveAV 的第七个主功能。它把两个资源通知群当前未读消息中的提取关键词合并去重，逐个发送到资源提取群，即时接收短时有效的 PikPak 回复，再把每个唯一资源整理为一条消息保存到指定收藏群。只有已经完整处理并成功保存的来源范围才允许确认已读。

本功能不同于第六功能“Svip PikPak 链接消息”：第六功能直接从 Svip 已有消息中提取链接；第七功能先从通知消息取得关键词，再到另一个群兑换链接。

## 私人会话配置

真实群组 ID 只保存在：

```text
LoveAV-Data/config/telegram-sources.json
```

需要四个稳定键：

```json
{
  "sources": {
    "pikpak_notice_updates": {
      "chat_id": "<资源更新通知群ID>",
      "title": "<资源更新通知群名>",
      "mode": "current_unread"
    },
    "pikpak_notice_share": {
      "chat_id": "<资源分享通知群ID>",
      "title": "<资源分享通知群名>",
      "mode": "current_unread"
    },
    "pikpak_extraction_group": {
      "chat_id": "<资源提取群ID>",
      "title": "<资源提取群名>"
    },
    "pikpak_collection_group": {
      "chat_id": "<当前收藏群ID>",
      "title": "pikpak链接收藏"
    }
  }
}
```

不得把真实群 ID、用户名、消息正文、PikPak URL、密码或 Telegram 凭据提交到 Skill 仓库。目标群必须按稳定 ID 唯一匹配；同名旧群、迁移前群或搜索第一项都不能代替当前目标。

## 调用与冻结未读

只有用户调用第七功能时才运行；Skill 不后台常驻，也不自动巡检。

每次调用先分别冻结两个通知群：

```text
lower = read_inbox_max_id_at_source_start
upper = latest_message_id_at_source_start
范围 = lower < message_id <= upper
```

冻结后到达的新消息不属于本轮，必须保持未读。两个来源分别保存自己的 `lower`、`upper`、消息数量和读取结果；一个来源失败不能伪装成两个来源都已完成。

## 关键词提取与交集去重

优先从 Telegram 的代码实体、主题标签实体以及“回复关键词 / 提取关键词 / 资源更新”附近的明确文本提取关键词。不得从普通标题任意猜词。

比较键按以下顺序规范化：

1. Unicode NFKC；
2. 去掉首尾空白；
3. 去掉最前面一个 `#`；
4. 合并内部连续空白；
5. ASCII 字母不区分大小写。

实际发送时保留首次出现的原始关键词；若原文没有 `#`，发送前补一个 `#`。

同一关键词可能同时出现在两个通知群，也可能在同一群重复。无论对应多少条来源消息，本轮只向提取群发送一次，但必须在任务中保留全部来源 `(chat_id, message_id)`。一个来源消息含多个明确关键词时，只有这些关键词全部成功，才算该来源消息处理成功。

没有明确关键词、关键词冲突或结构无法判断的消息进入 `review`，不得发送，也不得确认已读。

确定性计划器：

```powershell
python scripts/plan_pikpak_notification_redeem.py `
  --source pikpak_notice_updates=<通知群A未读快照.json> `
  --source pikpak_notice_share=<通知群B未读快照.json>
```

计划器只消费已经冻结的结构化未读快照，不连接 Telegram、不发送消息、不标记已读，也不保存完整正文。

## 发送与即时接收

资源机器人通常在发送关键词后 1～2 秒内回复，并可能很快自动删除消息。因此一次兑换必须由同一个 TG Exporter daemon 请求完成：

1. 在提取群发送一个关键词；
2. 从发送前就订阅新消息；
3. 等待到超时上限，同时收集与本次请求有关的回复；
4. 验证合法 `mypikpak.com` URL；
5. 绑定同一回复中的密码；
6. 对多机器人重复回复按规范 URL 与密码去重；
7. 返回明确的 `success`、`timeout`、`flood_wait` 或 `write_outcome_unknown`。

不能使用“执行一次 `send`，等待命令退出，再冷启动一次 `history`”的方式。这会因为启动耗时和回复自动删除而漏掉真实结果。写入结果未知时禁止自动重发关键词，以免重复触发机器人。

当前 TG Exporter 若没有“发送并即时捕获”能力，本功能只能生成去重计划和人工执行清单，必须明确报告执行器缺口；不得声称自动兑换完成。

## 资源成功条件与收藏群写入

一个关键词只有满足下列条件才算兑换成功：

- 至少捕获一个合法 PikPak URL；
- 每个资源的标题、链接和可取得的密码已经整理；
- 资源已经成功发送到当前唯一收藏群，或已确认该规范 URL 早已存在于该收藏群。

收藏群固定采用“一项资源一条消息”，格式为：

```text
<资源标题或关键词>
<PikPak URL>
密码：<密码>
```

没有密码时写 `密码：未提供`，不能猜测。一个关键词返回多个唯一 URL 时分别发送多条。发送前按规范 URL 检查本批重复和收藏群已有记录；已经存在的 URL 不重复发送，但可作为“已保存”成功证据。

本功能发送的是整理后的新文本，不是假装 Telegram 真转发。若用户另行要求保留原始转发来源、图片或排版，改走受确认保护的 `forward` 流程。

## 已读确认

已读是最后一步，并采用失败安全策略：

1. 只有来源消息关联的全部关键词都已兑换并保存，来源消息才成为 `ack_eligible`；
2. 两个群中的同一关键词只处理一次，但成功结果同时满足其映射到的所有来源消息；
3. 任何 `review`、超时、无链接、发送失败或写入结果未知都会让关联来源消息保持未读；
4. Telegram 已读位置通常只能单调向前，不能任意跳过中间失败消息。因此默认只有某来源冻结范围内的全部消息都 `ack_eligible` 时，才把该来源确认到冻结的 `upper`；
5. 若执行器能证明从 `lower` 开始存在连续成功前缀，也只能确认到该连续前缀的最后一条，绝不能越过第一条失败或待复核消息；
6. 必须回读或取得机器可读确认，才能报告“已标记已读”；
7. 快照后消息永远不在本轮确认范围内。

这就是“处理成功的可以已读，未处理成功的仍保持未读”的可实现语义。不能为了让已读数归零而越过失败项。

## 最终报告

每次至少报告：

- 两个来源各自冻结范围与未读数量；
- 提取出的关键词数量；
- 跨群及群内重复数量；
- 实际发送关键词数量；
- 成功、超时、无链接、待复核数量；
- 唯一 PikPak 资源数量；
- 收藏群新增、已存在、失败数量；
- 两个来源各自的已读确认上界，或保持未读的原因；
- 快照后新消息不在本轮范围的说明。

不得在报告或持久化日志中泄露 Telegram Session、API 凭据或 IPC 密钥。
